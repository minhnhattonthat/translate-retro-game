# PSP notes

Written from a rhythm game whose text was almost all pictures; a text-heavy game (RPG, visual novel) will also need the text pipeline in `pipeline.md`. Tools for every step below are in `$SKILL/scripts/`.

- **Image:** a UMD `.iso` (ISO9660; `.cso` is the same, compressed: decompress with `maxcso --decompress` first).
  - `iso9660.py list|x ISO ...` lists and extracts; `iso9660.patch(iso_in, iso_out, {path: bytes})` swaps files in place. A file that no longer fits goes to the end of the image and the directory record is repointed. Identity test: patch with the unmodified bytes and `cmp` against the original.
  - `PSP_GAME/PARAM.SFO` holds the title shown in the XMB: `sfo.py` reads it and rewrites strings in place (the title slot is 128 bytes, UTF-8). `ICON0.PNG` (144×80), `PIC1.PNG` (480×272) and `SND0.AT3` are the XMB icon, background and sound; they carry text as pictures too.
- **EBOOT.BIN is encrypted** (`~PSP` header). Do not hunt for a decrypter: PPSSPP dumps the decrypted ELF when `DumpFileTypes = 7` is set in `memstick/PSP/SYSTEM/ppsspp.ini` (section `[General]`) and the game boots. The dump appears in `memstick/PSP/SYSTEM/DUMP/<ID>_EBOOT.BIN`; set the value back to 0 afterwards. Strings in it are patched in place, each inside its NUL-terminated slot plus the zero padding after it. Check the encoding per string: UTF-8 and Shift-JIS both occur in one binary (`jpscan.py` finds Shift-JIS, UTF-8 and UTF-16; most hits in code are noise, real strings read as sentences). A shipped EBOOT does not have to be re-encrypted: PPSSPP and CFW run a plain ELF `EBOOT.BIN`, but ask the user before shipping that for real hardware.
  - Format strings (`%d`, `%4d`) must keep their count and order. A `\n` inside a string is a line break the game honours.
- **Containers.** Games commonly use CRI middleware: `.cpk` archives (`cpk.py list|info|rebuild`; `FileOffset` is relative to the lower of `ContentOffset` and `TocOffset`; the rebuild keeps 2048-byte alignment and patches the TOC, and its identity test (rebuild with no edits, `cmp`) passes on every CPK of the game), `.acb/.awb` audio, `.pmf` video. Inside a CPK expect game-specific wrappers, here `ARC\0` + per-file zlib. Identify an unknown wrapper by its header, then try `zlib.decompressobj` at each `78 9c`; reuse the original compressed block for unchanged files so unedited data stays byte-identical, and recompress edited ones at the level the original used (find it by recompressing an unchanged file and comparing).
  - UI layout files carry sprite names, positions, sizes and UV rects (here `MNUF`: object table at fixed stride, floats); read them to learn each sprite's on-screen box before redrawing text into it.
- **Graphics are GIM (`MIG.00.1PSP`).** `gim.py` decodes and re-encodes 4/8-bit indexed and 16/32-bit images, linear or swizzled (16×8-byte blocks); `gim.encode` writes the same number of bytes, so nothing else in the container moves. Check roundtrip over every GIM in the game before editing (decode → encode → decode must be pixel-identical; compare with fully transparent pixels normalised). Indexed images keep their palette when the new colours fit it, else a median-cut palette of the same size is written; fully transparent entries sit in the palette at fixed indices, so a text-in-palette trick (glow, outline) may need `repalette=True`. Embedded GIMs sit at arbitrary offsets inside unpack results: find them by magic, size from the block header at `+0x14`, and key each by `<file index>_<offset>`.
  - Same texture bytes appear once per song/level archive: dedupe by md5 and write the replacement to every copy (a `copies()` helper), or one song shows English and the rest Japanese.
  - The workflow that worked: unpack everything; contact-sheet every unique GIM (`showgim.py`; look at them, do not guess from names); classify (text / art / numbers); redraw text with `typeset.py` (Pillow; condensed fonts via `xscale` to match the original's tall narrow lettering, `dominant()` to copy the original colour, `inpaint()` to remove lettering printed over artwork); show original and replacement side by side (`showgim.py --new`); rebuild the ISO; look at the in-game shot.
- **Text drawn by sceFont / libfont:** a few strings may come from a table in the EBOOT or data files, rendered at run time with the system font (`libfont.prx` plus a JIS↔UCS table). Those are ordinary text work. Scan decompressed data for Shift-JIS and UTF-16 runs before concluding that everything is graphics.
- **Video (`.pmf`)** is H.264 in a PSMF wrapper (`ffprobe` reads it). Titles burned into movies (here song-name cards and a credits roll) are not fixable by editing images; re-encoding and re-muxing PSMF is its own project. List such movies in the graphics survey and ask the user whether to leave them.
- **Save data:** the PSP system save dialog and the game's own prompts are separate. The game's prompts are GIMs; the dialog is the firmware's and follows the console language. Saves land in `memstick/PSP/SAVEDATA/<ID>DATA00` and persist between emulator runs: use `--clean-saves` for a fresh-install run.
- **Emulator and QA:** PPSSPP through `emu.py game.iso` (details in `emulator-qa.md` §PPSSPP). The Japanese button convention applies: **circle is OK and cross is cancel** in most Japanese games; the driver sends raw buttons.
- **Release:** xdelta3 against the original ISO (an ISO is ~1 GB; a few changed CPKs produce a patch of a few hundred MB because archives are re-laid out. If the player's tool cannot take that, patch per file instead). README lists the base ISO hash, and says the patch needs an unmodified dump.
